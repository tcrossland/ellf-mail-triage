relies on, with its source and the date it was checked. Anything not checked
is **unverified**.

| Firefox needs the cluster's CA imported into its own certificate store; Chrome and the macOS keychain share trust. | Tried | 2026-11-20 |

| `ellf publish data` without a destination stores the file as `<name>-<version>`, without its extension, and a recipe then can't choose a loader. Pass a destination path that keeps the extension, and `--loader jsonl` for JSONL. | Tried with ellf-cli 24.0.0 | 2026-11-20 |
| Existing answers load into a new dataset with the `db_actions` recipe (`--copy.in-asset`), from a JSONL asset with `text`, `label`, `answer` and `_view_id`. | Tried with ellf-recipes on 2026-11-20 | 2026-11-20 |
| A label scheme is an asset of kind `labels`: a JSON object from each label, in order, to its `description`, `do_not_mark` (what not to give it) and `examples` (`text`, with `label` when the label applies). Guidelines are a markdown asset of kind `instructions`. The `textcat` task takes `--label-scheme` and `--settings.instructions`, with `--labels-exclusive` for one label per message; annotators see a label's description on hover. | ellf.ai/docs/assets-files#labels; `ellf tasks create textcat --help` with ellf-recipes on the cluster; helpdesk-routing's README | 2026-11-20 |
| `gemini_agent` and `hf_llm_agent` use the label definitions and instructions of the task they are assigned to, and can add their own scheme and instructions on top. `review` takes a typed `--label` list, or else the labels found in the answers. `train` takes its labels from the answers (`--textcat.train` for exclusive labels) and can draw a learning curve (`--train-curve`). | ellf.ai/docs/assets-files#labels; `ellf agents create`, `ellf tasks create review` and `ellf actions create train --help` | 2026-11-20 |
| `ellf publish data` with `--kind labels` and `--kind instructions` publishes a label scheme and guidelines; give a destination path that keeps the extension. Assets belong to the cluster: the command takes a project only for `--render`. Publishing under an existing name with a new `--version` adds a version to that asset; `ellf assets info` shows the latest. | Tried with ellf-cli 24.0.0 | 2026-11-20 |
| `ellf publish code DIR` builds the package with whatever `python` is on PATH and then imports it to read its recipes, so it needs a Python with setuptools, Prodigy and `ellf-recipes-sdk`, as the docs' recipe development setup installs (`pip install prodigy ellf-recipes-sdk ellf-recipes`). Without them it stops with no module named setuptools, or no module named ellf_recipes_sdk. | ellf.ai/docs/recipe-development#setup; tried with ellf-cli 24.0.0 | 2026-11-20 |
| Prodigy comes from Ellf's private package index. `ellf login`, run with the virtualenv active, writes `$VIRTUAL_ENV/pip.conf` pointing pip at it through a keyring backend (no secret on disk), but only if the venv's pip is 26.2.2 or later; with an older pip, or none (a uv venv), it skips this with a warning. `python -m ensurepip` installs a pip too old for it (25.0.1 with Python 3.12). | Tried with ellf-cli 24.0.0 | 2026-11-20 |
| On the index, `ellf-recipes-sdk` 1.3.211 calls `Database.count_legacy_examples`, which the latest stable Prodigy (1.18.29) lacks: recipe tests that save examples fail with an `AttributeError`. They pass with the pre-release `prodigy==2.0.0a18` (`pip install --pre`). | Tried with the github-docs-issues venv, Python 3.12 | 2026-11-20 |
| When several versions of an asset share a name, a task or action given the name doesn't say which it uses; given a version's asset ID it uses that version (`--label-scheme` with the 0.2.0 ID gave the task that version's six labels, logged as "Add multiple choice options for 6 labels"). `ellf tasks info` shows the name, not the version. `ellf actions stop` leaves the action in state `not_found`, and an action that saves at the end saves nothing when stopped. | Tried with ellf-cli 24.0.0 | 2026-11-20 |
| A task's `--input` takes an asset's ID as well as its name, which picks one asset when two share a name. | Tried with ellf-cli 24.0.0 | 2026-11-20 |
| `hf_llm_agent` does not run a model on the cluster: it calls a chat model on Hugging Face Inference Providers (by default `meta-llama/Llama-3.3-70B-Instruct`), billed to your Hugging Face token, so the mail goes to Hugging Face and the provider it routes to. No built-in agent runs an LLM on the cluster; `hf_model_agent` (in `ellf-recipes-gpu`) runs a fine-tuned transformers text classifier, not an LLM. | `ellf agents create hf_llm_agent --help` and `hf_model_agent --help`; `ellf recipes list` | 2026-11-20 |
| Ollama is MIT-licensed and serves an OpenAI-compatible API on `127.0.0.1:11434`. On a Mac the Lima VM reaches it at `host.lima.internal`, which is `192.168.5.2`; a pod in the cluster reaches `192.168.5.2` but can't resolve the name. So a local model needs no port open to the network. | Ollama's `LICENSE`; tried with Ollama 0.40.16 and Lima 2.3.0 | 2026-11-20 |
| Qwen3-8B and Qwen3-14B are Apache-2.0. Ollama's library page for qwen3 states no licence. Gemma 3 is under Google's own Gemma terms, which are not read. | huggingface.co/Qwen/Qwen3-8B and /Qwen3-14B, and their `LICENSE` files; ollama.com/library/qwen3; huggingface.co/google/gemma-3-12b-it | 2026-11-20 |
| Qwen3 through Ollama's OpenAI-compatible endpoint thinks first by default: the reasoning comes back in a separate `reasoning` field and the answer alone in `content`, but a reply takes 15 to 70 s on an M2 with 24 GB, for 8B and 14B, some longer than `llm_to_dataset`'s 60 s timeout. `/no_think` in the prompt does not turn it off; `"reasoning_effort": "none"` in the request does, and a reply then takes about 0.5 s (8B) or 1 s (14B) on short messages, after a first call of 5 to 9 s that loads the model. `llm_to_dataset` sends neither. On the label scheme's 10 synthetic examples, 14B without thinking got all 10, 8B without thinking 8 (twice it gave two labels). | Tried with Ollama 0.40.16, qwen3:8b and qwen3:14b, with `llm_to_dataset`'s prompt | 2026-11-20 |
| Hugging Face does not store the request or response it routes through Inference Providers, and keeps debugging logs without user data for up to 30 days; it does not train on them. Each provider's own data policy applies, and HF does not say what those are; for language models OpenRouter picks the provider. There is no zero-retention option; you can turn providers off in your account settings, and a pinned provider is never swapped. The providers' own policies are **unverified**. | huggingface.co/docs/inference-providers/security, /routing and /providers | 2026-11-20 |

| llm-classifier-eval's `llm_to_dataset` action (MIT, in its `recipes/`) saves an LLM's answer on every text of an input asset to a dataset, credited to its own annotator session, so the review and dashboard compare it with a person's. It calls any OpenAI-compatible endpoint (`--base-url`, `--model`, optional `--api-key`), or reads a label already in each record's meta (`--llm-label-key`), which would also load Gmail's categories as an annotator. It sends the label scheme's definitions and `--instructions`, not the task's guidelines asset. | Its README and `llm_to_dataset.py` in explosion/ellf-templates | 2026-11-20 |
| Gmail's categories are lopsided in a real archive. Of a Gmail account's categorised mail, Personal (Primary) holds 72%, Updates 27%, Forums 0.4%, Promotions 0.3% and Social 3 messages; of a Google Workspace account's, Updates 50%, Forums 22%, Personal 21%, Promotions 7% and Social 1 message. Whether bulk mail sits in Personal or Updates is not checked. | Count-only queries on two real backups | 2026-11-20 |
| Gmail's categories do not stop at 2013, when its tabs launched: in a real Gmail backup, received mail carries a category from October 2010 (a few from July to September 2010) and none before; from then on, mail without one is almost all sent mail or drafts. A second account shows the same from 2010 to 2011. So the slice without Gmail's categories is mail from before late 2010, not before 2013. | Count-only queries per year and month on two real backups | 2026-11-20 |
| A Google Takeout mbox gives each message's Gmail category, in its `X-Gmail-Labels` header: comma-separated labels, a category named like `Category Promotions`, chats labelled `Chat`, sent mail `Sent` and drafts `Drafts`. The importer accepts this and the `CATEGORY_PROMOTIONS` form. | Third-party guides to Takeout mbox files; no real export checked | **unverified** |
| A Got Your Back backup (db_version 6) keeps each message's labels in the `labels` table of `msg-db.sqlite`, system labels by Gmail ID, so a category is `CATEGORY_PROMOTIONS` and so on; messages are `<year>/<month>/<day>/<gmail_id>.eml`, and chats aren't backed up. In two real Gmail backups all five `CATEGORY_` labels occur, 77% and 89% of messages carry one, almost always exactly one (one message in about 7,500 had two; the importer then takes the first of personal, social, promotions, updates, forums), and none has a chat label. Sent mail carries `SENT`, drafts `DRAFT` and deleted mail `TRASH`: in one Gmail backup 12% of messages are sent mail, three quarters of it without a category, and 32% are in the trash. Backups of non-Gmail accounts have no categories. | mailcellar's `backup/gyb.py`, from gyb 1.97's code; count-only queries on four real backups | 2026-11-20 |
